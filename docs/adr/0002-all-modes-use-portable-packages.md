# ADR 0002: Every mode is a portable package

- Status: Accepted
- Date: 2026-09-22

## Decision

Every user-facing module must be exportable as one portable Mode Pack. The pack may contain multiple internal phases/profiles and must be decomposable into installable components. Its specialized harness, route validation and frontend are first-class package assets with versioned identities, entrypoints, dependency edges and verified bytes. They cannot be silently assumed to exist in the target host. Code Mode is the first implementation instance, not a separate packaging contract.

An exported pack targets a declared operating system and architecture. It includes the complete bytes of every **mode-owned** local component and a dependency graph describing how those components fit together. A dependency supplied by the target host is allowed only when explicitly declared as an external prerequisite. Import preflight checks those prerequisites, reports missing or incompatible items to the Pi agent, and cannot mark the import successful until they are resolved. Cloud services remain external. Missing package content must never be silently downloaded at first activation.

A successful import makes the module, its phases, specialized harness, route validation and frontend usable immediately, without rebuilding or restarting pi-own. These assets must therefore be installable runtime content behind a stable host capability interface; a source tree that needs a new Next build is not an installable frontend artifact.

Editing a built-in mode updates that mode's existing identity. The definition store retains one current definition per mode ID, not an original-plus-copy pair. A multi-phase module advances all of its phases together. Revision numbers provide optimistic concurrency; older content-addressed archives remain available only to already committed session snapshots. Unlinking a default Skill removes it from the current definition and the next exported archive. A package Skill may also be selected into another mode's complete package without renaming the Skill.

Catalog-backed local built-in Skills are user-editable source. If their bytes change, a dormant session restart creates and journals a fresh binding before the Agent starts; custom catalog-backed definitions advance their current revision on resolution, and remain selectable while that refresh is pending. This does not change historical snapshots or loosen portable archive pins. Missing Skills and drift in other resource kinds remain activation errors.

## Why

A Code-only package would make mode identity depend on which frontend and host features happened to be built into pi-own. A common package boundary lets a mode move to another compatible installation as one experience while still allowing its components to be reused.

A matching function or component name across two packages is not enough to reject import. Different implementations may coexist behind mode/package scopes. Shared-component reuse requires an explicit component identity, version/content evidence, and compatible dependency edges. If two packages expose the same public tool, command, or capability name in one active session, the host adds deterministic package-name prefixes to disambiguate them. It records the mapping and verifies that every selected capability can still be invoked; upstream package content is not rewritten. This collision alone does not fail import. **Skills never receive a package prefix**: their visible names remain the original upstream names, with source/version/hash recorded separately for verification and reuse.

The package boundary is a complete user-facing module. The two education-related modules are **Course Builder / 备课** and **Study & Research / 学习与研究**. `study-research.study` and `study-research.research` are phases of the latter, not two packages. Historical IDs such as `student-learn`, `practice`, `teach-back`, `visual-lab`, and `teacher-prep` are course-bound profiles/workflows inside the learning harness, not five additional modules to export independently. General, Creative, and Code are separate user-facing modules, as are saved custom modules. A module package may contain multiple internal profiles and its own frontend; `frontend: null` is valid only when it genuinely has no special UI.

## Implemented boundary

The common constructor/parser and streamed `.mode-pack.tar` format carry verified component bytes, frontend assets, exact target OS/architecture, external executable prerequisites, optional offline npm runtime and package-owned harness/route-validation assets. A module may have several internal profiles. Import stages immutable payloads, verifies hashes and selected Skills, loads the runtime entrypoint, checks its route and extension exports, then registers every profile atomically. Renamed installations share content-addressed bytes. General and Creative use this same format; Code includes its pinned Skills/extensions and offline npm tree. Course Builder and Study & Research each export one module with a compiled frontend and backend route/extension closure. Their imported sessions can be activated without a new Next build.

Package frontends run in an opaque, snapshot-bound frame. Package API calls and ordinary downloads are bound to the active session's package route; downloads are fetched by the verified parent so the frame never receives host-origin authority. Host interfaces required by packaged frontends are declared and versioned in `projectCapabilities`: `host-api:cwd-browse@1` and `host-api:pdf-preview@1`. Import preflight rejects an unsupported interface; package pages cannot acquire arbitrary host API access. The PDF viewer, PDF.js worker, fonts and maps travel as package frontend assets. The viewer requests JSON preview content through the package frame and parent bridge, which reads bytes from the active package route. Spec Kit remains an optional project capability.

New archives also carry a canonical `dependencyGraph` in the signed package identity. Its nodes include every profile, resource, file, frontend, package runtime asset, npm pin and declared host/executable prerequisite; its edges bind each consumer to its local or host dependencies. Import recomputes the graph from verified manifest fields and rejects any missing or altered node or edge. Older archives without a graph remain readable for migration.

Cross-package sharing is opt-in through `sharedResources`. A binding identifies one bundled resource by a logical ID, enumerates its entry and supporting file closure, and lists exact stable-semver versions the owning module explicitly accepts as upgrades. Private resources with identical names remain independent. Import compares the candidate with currently installed providers before staging and again under the store commit lock. The newest version is selected only if every older consumer accepts it; different entry or supporting bytes at one version and undeclared upgrades fail with a structured comparison of installed Pi providers. New sessions use the selected provider's verified bytes, including Skills and extension entrypoints. Each original package still carries its own full bytes and original pin, so it can be exported standalone and historical snapshots can continue to resolve their exact provider. Successfully installed shared-provider hashes remain registered for committed snapshots after that provider mode is removed; retained hashes do not join current-version arbitration.

Each imported package has its own resource scope. A matching Skill name in another mode does not require a prefix or block installation. Within one mode, two selectable providers of the same Pi Skill name fail preflight because Pi's native loader otherwise uses first-wins resolution. Public tool and command collisions within one candidate session receive deterministic provider prefixes before Pi registers them. The system prompt is replaced for ordinary non-coding modes, preventing Pi's coding preamble from leaking into Study or Course Builder.

Before committing an import, the host loads the incoming package's extension factories in a disposable Pi agent directory and checks their actual public registrations, including host-reserved tools. A shared extension upgrade also rechecks every installed peer mode that would bind to the new provider. Tool and command collisions are qualified with provider identities, including compiled `module-runtime/extension-*.mjs` entries. Flag and shortcut collisions stop import with a structured diagnostic; Pi must never silently choose a winner. The probe is compiled into the host's published runtime, so this preflight does not depend on repository TypeScript files at the destination. Package runtime entrypoints do not construct the host's built-in Skill catalog at module import.

Import failures provide structured `Conflicts happen … install failed.` diagnostics and a prepared resolution prompt. The import API sends that prompt to the initiating Pi session where possible and exposes it for manual dispatch when delivery fails. No failed package is registered.

## Remaining work

Shared-resource upgrades currently require an explicit list of exact accepted stable-semver versions; a commit-style version can share only on exact version, entry hash and support-file closure, because no "newest" ordering is defined. Semver ranges and npm-backed shared resources are not yet part of that contract. An extension that registers new public names only after activation is guarded by the live session registration map; static import preflight cannot predict names that depend on future model or session data.

Course-bound learner profiles remain internal to the learning harness, not independent user-facing packages. Any reusable module that needs those host services must declare a stable versioned host interface or carry the local implementation bytes. Course Builder and Study & Research were validated across agent directories on Windows; registration preflight also checked both modules and affected installed peers before commit. Browser checks cover activation, both workspaces, a package-local PDF preview, an exported download, and linking a browsed folder. Package transfer tests do not by themselves certify every feature inside a module: the optional workspace-history `/undo`/`/redo`/`/tree` flow and the full Course/Study action matrix require their own feature acceptance.
